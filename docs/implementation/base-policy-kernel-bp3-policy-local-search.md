# BasePolicyKernel BP3：Policy-local 搜索与 stun 量词

## 结论

BP3没有调Minimax分数或胜率阈值，而是把V1搜索合同进一步压入一个固定数组的
policy-local视图：根动作集合、敌方列顺序、深层动作集合和我方stun结果都不再由
ProductionRoot候选行的偶然布局决定。

固定16场景结果表明这次结构修改同时改善了动作质量和搜索完整度：

- 根我方动作集合为1,265/1,304（97.01%），敌方为1,299/1,304（99.62%）；
- 完整战术动作一致率由BP3早期的1,423/1,791（79.45%）提高到
  1,627/1,925（84.52%）；
- 完整支持根上的pairwise排序由65/69提高到99/110，best action由22/25提高到
  33/38；
- 我方stun不再枚举两个ChanceOutcome。V1语义是比较正常/反向落点的即时风险后，
  确定性保留对我方更坏的一个结果；
- 同轨Shadow的节点由321,620降至299,270（-6.95%），budget leaf由126,513降至
  104,624（-17.30%），P95由20,132us降至17,877us（-11.20%）；
- 所有诊断路径保持零热分配，root restore与四项硬不变量均为0。

## ACTIVE POC

同一固定16场景、32局：

| 模式 | 胜/负/平 | 分析得分 | FIRE | 动作数 | 候选总耗时 |
|---|---:|---:|---:|---:|---:|
| 当前V2基线 | 2/28/2 | 9.38% | 151 | 3,030 | 1,138,635us |
| BP3早期policy-local | 14/16/2 | 46.88% | 172 | 2,708 | 15,415,540us |
| BP3 + V1 deterministic stun | 15/16/1 | 48.44% | 231 | 2,907 | 16,501,998us |

最后一行相对当前基线为`+39.06pp`，相对BP3早期版本为`+1.56pp`。总耗时不能直接
按两次不同轨迹比较：新版本多执行199个动作。按候选动作归一化约从5,693us降至
5,677us；ACTIVE P95从17,231us到17,941us，因此这里只能认定“节点成本没有明显退化”，
不能据此通过production性能门。

## 结构判断

BP3证明“Minimax太强所以输”不是准确诊断。此前弱点主要是V2让错误的状态量词、
动作域和tie-break进入强搜索；当这些合同接近V1后，固定场景得分从9.38%恢复到48.44%。

剩余成本也不能靠降低depth处理。ACTIVE轨迹中原生搜索仍有266,617个节点和91,888个
budget leaf，而V1递归为227,894和49,138。下一阶段应先拆分：

1. V2 `TACTICAL_CONTACT`比V1实际进入战术搜索的根更宽，先建立逐根调用资格差分；
2. 对共同根逐行动比较V1每根`AT_NODE_LIMIT`与原生per-root预算消耗；
3. 分离“多搜索了不该搜索的根”和“同根每节点更贵”，不得用统一减深掩盖；
4. 只在调用域一致后再设计迭代加深和中断保存最后完整层。

BP3仍是诊断实现，不进入production默认。ProductionRoot SHA-256保持
`c4443ddbd2a7a651d77f1582e5b68ce3715dfc87af7cf40ac7432396def39c48`。

