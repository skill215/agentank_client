# HP24：无效GO后继别名实验拒绝

## 结论

HP24尝试复用同一根中已经缓存的敌方`NONE`后继：若敌方`GO`已被公共物理规则严格证明为
no-effect，且相同我方动作的`NONE`后继已经存在，就复制其delta和Hard元数据，避免再次构建
完全相同的`GO`后继。

这个别名在测量样本上是精确的，但不是有效的生产优化。固定16个标定根的144个候选联合后继中，
63个满足谓词，63个都与完整构建的状态、Hard和terminal一致，假阳性为0。然而真实32局仅命中
19次：只把19次build/Hard fill换成replay，确定性work减少57/4,471,793，约0.0013%；搜索节点、
完成深度、值支持深度、动作、星数和胜负全部不变。

五批标定先跑OFF再跑ON时曾出现表面加速，但反转运行顺序后消失。反向对照中Physical P1–P6的
cold P95变化为`+4/+30/0/+37/+26/+30us`，warm P95为
`+5/+16/+44/+47/+41/+42us`。因此这不是稳定收益，而是运行顺序和本地墙钟噪声。

结论为：完整撤销HP24运行时代码，不保留默认开关或热路径分支；HP23语义、源码指纹和标定基线
全部恢复。机器证据保留，用来约束后续不要重复尝试这个局部优化。

## 为什么节省量如此小

这个方案只有在三个条件同时满足时才工作：

1. 当前敌方`GO`被证明为no-effect；
2. 相同我方动作的敌方`NONE`后继已经在同一个root slab中建立；
3. 当前访问顺序恰好先计算了该canonical cell。

标定会重复遍历规则密集的固定根，所以累计得到1,665次命中；真实arena中不同根、不同动作顺序和
早停把机会压缩到32局19次。更关键的是，节点预算仍把这个联合动作视为一个节点，值计算和递归也
没有消失，因此只省下一次很小的Fast/Hard构建，无法让Minimax完成更深一层。

## 因果数据

固定16场景、32局，同源码alias ON/OFF：

| 指标 | ON | OFF | 变化 |
|---|---:|---:|---:|
| 胜/负/平 | 3/28/1 | 3/28/1 | 0场转换 |
| 星差 | -42 | -42 | 0 |
| FIRE | 150 | 150 | 0 |
| 搜索节点 | 26,912 | 26,912 | 0 |
| alias命中 | 19 | 0 | +19 |
| build | 21,511 | 21,530 | -19 |
| Hard fill | 21,507 | 21,526 | -19 |
| work | 4,471,736 | 4,471,793 | -57 |

动作流、帧、终局原因、完成深度和值支持直方图零差异；replay失败和热分配均为0。墙钟ON反而更高，
但由于本地漂移较大，只把反向顺序的“不稳定/无改善”和确定性work节省过小作为拒绝依据。

## 后续方向

HP23增加的成本不是一个root cell重复构建造成的。下一步先做按搜索层级和操作类别的成本census，
至少区分：

- root replay / Fast build / Hard classify；
- Successor-TT hit与真实展开；
- terminal/leaf evaluation；
- 深层代表动作和联合Chance展开；
- 预算中断前最后一层的无效工作。

只有证明某类工作同时占显著比例并阻止请求深度完成后，才进入HP25实现。优化仍必须保持节点值、
动作、Hard、Proof和root restore语义一致；不能用降低深度冒充提速。

机器证据见`config/engine-v2/hp24-no-effect-go-alias-rejection-evidence.json`。
