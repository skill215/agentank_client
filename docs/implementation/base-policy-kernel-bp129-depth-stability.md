# BP129：Minimax深度/预算稳定性标定

BP129没有更换候选，也没有按不同深度重新选动作。它对BP128中完全相同的211组
`incumbent/candidate`，依次运行四条预注册lane：depth1/2048、depth2/256、depth2/2048和
depth3/2048。每条lane使用独立TT generation，避免前一条lane预热后一条；结果写入固定数组，整局
动作、胜负、星、击毁与production hash均不变。

## 结果

| lane | 完整/不完整 | higher/equal/lower | 合计节点 | 最大单根合计节点 |
|---|---:|---:|---:|---:|
| D1/B2048 | 211 / 0 | 31 / 110 / 70 | 8,820 | 72 |
| D2/B256 | 211 / 0 | 64 / 109 / 38 | 20,907 | 512 |
| D2/B2048 | 211 / 0 | 64 / 109 / 38 | 21,311 | 672 |
| D3/B2048 | 30 / 181 | 18 / 6 / 6 | 24,472 | 4,096 |

同深度把预算从256扩大到2048后，211个关系全部不变，只多计算404个节点。由depth1升到depth2时，
41/211个根改变关系；由depth2升到depth3时只有30个根能完整比较，其中8个改变关系。

关键是181个depth3不完整根总共只尝试11,244个节点，最大单根合计470，预算命中为0。唯一用满
4,096个合计节点的是一个已经完整的根。因此depth3的主要阻塞不是“节点用完”，而是在更深一层遇到
当前policy/transition不支持闭合的世界线。

历史方向也没有随加深改善。depth2的64个正scalar是2改善、2退化、60不变；depth3完整子集的18个
正scalar是0改善、1退化、17不变。深度更高没有把点值变成可靠证书。

## 结论

- 拒绝通过扩大depth2预算提升这一类根；
- 在闭包语义完成前拒绝把production直接升到depth3；
- 保留固定pair标定工具，任何Minimax语义修改后都必须重新运行；
- BP130优先分类181个不完整出口，区分事件尚未结算、committed deadline未到、动作域缺失和叶区间
  未定义，再设计event/deadline quiescence与显式上下界。

这一步说明V2 Minimax的问题不是单纯“太早fallback”。在这一根族上，增加资源不会改变depth2判断，
而盲目加深会暴露更多语义不闭合并让符号不稳定。机器证据见
`config/engine-v3/base-policy-kernel-bp129-depth-stability-evidence.json`。
